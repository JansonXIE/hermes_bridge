04 / REVIEW RULES

审核规则 已实现·待部署

审核输入：不只采信开发总结

  • 原始需求原文（由 Hermes 在创建工作流时保存，不是开发组转述）。
  • 验收标准及其版本号，逐项带 ID。
  • 实际代码差异：审核组自己检出指定 revision 并与父提交比较（git show / git diff <sha>^ <sha>），不使用开发组提供的 diff。
  • 项目规范：项目内的 CLAUDE.md、编码规范、提交规范路径（项目配置提供）。
  • 自测证据：标注为“开发组提供，待核实”。
  • 已知风险和上一轮审核报告（返工轮次）。

固定审核对象

  • 项目、目标分支、Change-Id、revision SHA、Gerrit 链接（来自 push 输出）。Change 编号与 Patch Set 编号能从 push 输出或 git ls-remote 得到时一并记录，不是必需项；审核对象以 Change-Id + revision SHA 为准。
  • 基线版本：Patch Set 的父提交，以及审核时目标分支的提交。
  • 验收标准版本。
  • 审核开始前检出指定 revision 并核对 HEAD 等于 revision SHA；同仓库的开发任务直接按 SHA 建 worktree，外部 Change 用 git fetch + checkout 或 cherry-pick；拿不到或不一致即“审核受阻”。
  • 报告中的审核对象必须与任务记录逐字段一致，否则报告作废。

检查范围

  • 遗漏需求：每条验收标准是否都有实现与证据。
  • 边界与异常：空值、越界、超时、并发、错误路径、资源释放。
  • 权限与安全：输入校验、凭据、越权、注入、敏感信息日志。
  • 兼容性：接口 / ABI / 配置 / 数据格式、其他平台或分支。
  • 架构约束：分层、依赖方向、项目明确禁止的做法。
  • 测试是否被削弱：删除或跳过用例、放宽断言、改期望值迎合实现、注释掉检查。

测试策略

  • 项目当前没有 CI 门禁，报告中 ci.status 默认为 none。以后有 CI 时，只复用对应 revision 的结果，不采信开发组自述。
  • 按风险补测：对改动路径做针对性功能测试，对受影响模块做必要回归，不机械重复全部测试。
  • 板端 / 硬件等环境不可用时，相关验收项标记 未验证 并写明原因。
  • 每条测试记录命令、范围（针对性 / 回归）、结果和日志引用。
结论（verdict）前提业务状态
approve_recommended 建议通过无阻塞级问题；所有必需验收项为“通过”；无测试削弱；CI 状态不是失败待人工批准
changes_requested 要求修改存在阻塞级 / 重要问题，或有必需验收项“失败”要求修改 → 按策略返工
blocked 无法判断环境或证据不足、必需验收项“未验证”、审核对象不一致、无法拉取代码等审核受阻 → 人工处理

审核组权限 已实现·待部署

  • 审核任务在项目配置之外追加 disallowed_tools：Edit、NotebookEdit、Bash(git push:*)、Bash(git commit:*)；保留 Write 用于写报告文件；允许编译和运行测试。
  • 任务结束后 Worker 检查：HEAD 仍是被审核的 revision、被跟踪文件没有改动（git status --porcelain，未跟踪的构建产物不算）、工具日志里没有 git push；任一不满足则报告作废、标记“审核受阻”。
  • 审核报告写入 .bridge/review-report.json；.bridge/ 由 Worker 加入仓库的 info/exclude，不会进入提交。
  • 说明：工具规则对任意 shell 命令不是强制隔离（见“风险与待办”），以上是约束加事后校验。

返工规则

  • 原则上更新原 Change：返工任务用 continue_task_id 续接开发任务的会话与 worktree，按审核问题修改后 git commit --amend（保留 Change-Id），再按 gerrit-submit 规则 push 到同一 refs/for/…，产生新 Patch Set；新开 Change 需 Hermes 明确说明理由。
  • 新 Patch Set 出现后，旧结论自动失效，不得放行；基线变化也要重新检查集成风险。
  • 返工次数上限 max_rework_rounds（默认 2，可按工作流设置）。
  • 超限、范围扩大（改动文件或需求明显超出原需求）、高风险（安全、数据、接口兼容）时转人工处理。
  • 授权策略 rework_policy：confirm（默认，先通知用户确认）或 auto（上限内自动返工）。

workflow_id

一个需求一条工作流，贯穿开发、全部审核轮次和返工。所有任务、报告、通知都带 workflow_id。

parent_task_id

审核任务指向被审核的开发 / 返工任务；返工任务指向触发它的审核任务。形成可追溯的链条。

review_round

审核轮次从 1 开始，每个新 Patch Set 一轮。(workflow_id, revision, round) 唯一，防止重复创建审核。

状态迁移由桥接服务按上表校验并记入 workflow_transitions，每条迁移记录触发它的 event_id 或决定 ID；同一触发重复到达时直接返回已有结果。桥接服务只校验“迁移是否合法”，不评判代码是否合格。
06 / TASK LIFECYCLE

从提交到自动回传

提交并立即返回任务编号

Hermes 调用任务工具；服务验证项目权限和请求幂等键，将任务落库后返回 task_id，任务先进入 queued。

领取任务并启动进程

Worker 原子领取任务、设置租约，准备独立工作目录，使用参数数组启动 Claude Code，并记录执行尝试编号。

持续采集执行事件

分别消费 stdout / stderr，按行解析结构化输出。记录事件序号、最近动作和日志；阶段更新节流汇总，详细日志保留在桥接服务。

持久化最终结果

结合最终结果事件、错误信息及退出码判定执行状态。保存摘要、变更引用、测试结论和产物位置；CLI 成功不等于业务验收通过。

可靠通知并唤起 Hermes

在同一数据库事务中保存终态和通知 Outbox。投递器重试发送，接收适配器持久化并去重后确认，通过 Hermes 支持的消息或调度入口触发后续处理。

开发、审核、返工任务都走这条生命周期 已实现。新增角色 已实现·待部署 只改变第 1 步的输入校验、第 4 步保存的结构（开发证据 / 审核报告）和第 5 步的事件类型；业务状态另见“状态与关联”。

执行状态模型（单个任务）

queued→starting→running→succeeded / failed

取消：queued → cancelled；starting / running → cancelling → cancelled。超时：执行状态 → timed_out。进程归属无法确认时进入 recovering，核对完成前不直接重跑。

仅在能够可靠检测并具备交互恢复能力时增加 input_required；不要假设非交互 CLI 能在任意权限提示处暂停并自动恢复。
07 / MULTI-INSTANCE CONTROL

可以并行，但必须有边界

并发与预算

初始可设 max_concurrency = 3，超过限制进入队列。按机器负载、模型配额与任务成本调整；该数值只是配置示例。

目录与资源隔离

同仓库使用独立 Git worktree 和分支。端口、数据库、缓存另行隔离；不可信任务使用容器或更强沙箱。

依赖与合并

任务支持 depends_on。依赖失败时阻止下游自动执行。合并由单独串行任务完成，处理冲突后重新运行测试。integration 任务只合并任务分支，不合入目标分支；目标分支的合入由用户在 Gerrit 完成。

监控信号代表什么处理方式
Worker 心跳 / 租约执行器是否可达、是否仍拥有任务租约失效后核对进程，不盲目重复执行

阶段 / 工具执行摘要当前观察到的工作内容展示最近动作，不虚构百分比或内部思考

11 / DELIVERY & SECURITY

自动同步不只是一条 Webhook

至少一次投递 + 幂等消费

  • 结果与 Outbox 同事务提交，避免完成后漏通知。
  • 指数退避重试；超限进入待人工处理队列。
  • Hermes 接收适配器使用 event_id 去重。
  • 先可靠入队再应答；会话执行由独立消费者处理。

同一会话串行处理

  • 多个任务同时完成时，通过会话队列串行唤起。
  • 正在运行的 Hermes 回合不直接被修改历史。
  • 按任务关联结果，可短窗口合并通知。
  • 业务副作用也需幂等，不宣称端到端恰好一次。

进程与故障恢复

  • 原子领取任务，租约配合执行尝试编号防止旧 Worker 写回。
  • 取消先温和停止进程组，超时后强制终止。
  • 重启后核对执行器、进程身份和已保存事件。
  • 未知任务先恢复核对；带副作用任务不默认重跑。

权限与数据保护

  • 低权限账户、目录白名单、受限凭据与网络访问。
  • 不默认启用绕过权限确认的参数。
  • 回调地址由服务端配置，防止 SSRF；签名与防重放。
  • 日志脱敏；代码、输出和产物作为不可信输入处理。
12 / FAILURE HANDLING

工作流故障处理 已实现·待部署

事件幂等与有序

  • 沿用 V1.0：终态与 Outbox 同事务、指数退避重试、适配器按 event_id 去重、同一 Hermes 会话串行唤起 已实现。
  • 新增业务层幂等：审核任务唯一键 (workflow_id, revision, round)；返工任务唯一键 (workflow_id, report_id)；人工决定唯一键 source_ref（同一条微信消息）；状态迁移唯一键 (workflow_id, cause_id)。
  • Hermes 重复收到同一事件时，再次提交会得到已有任务（idempotent_replay: true），不会多建任务。
  • 同一工作流的事件按 occurred_at 和轮次处理；过期轮次的事件只记录，不推动状态。

结论只对指定版本有效

  • 审核进行中本系统推送了新 Patch Set（或用户告知外部推送）：该审核任务结果标记 stale，不推动状态；按新 revision 开新一轮。
  • 建议通过后出现新 Patch Set：回到待审核，旧结论不得放行。
  • 基线变化（目标分支前进、rebase）：重新检查集成风险，必要时补测。
  • 合入核对时 git fetch 失败：保持 awaiting_merge，告知用户稍后再核对，不推断“已合并”。

  • 花费：最小一次调用约 0.2–0.5 美元，大型 review 很容易超过 5 美元。工作流每轮至少包含一次开发和一次审核，返工会成倍增加费用。
  • 审核独立性：开发组与审核组使用同一模型、同一账户，独立会话和独立目录只能减少上下文污染，不能替代人工评审。
